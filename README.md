# バックエンドサーバー

## 特プロ（デジタルツイン）Cグループ

2025年夏の特プロ（デジタルツイン）において、Cグループは、湘南藤沢キャンパスの課題解決を目指してゲームを制作します。このゲームは、キャンパスの実空間に所在する人々の位置をリアルタイムに取得し、この人々と一番先に接触することをバーチャル上でプレイヤーに競わせるものです。ゲームの趣旨や詳細に関しては本リポジトリ外のドキュメントなどに説明を譲りますが、マルチプレイを想定していることなどから、バックエンドサーバーとクライアント（フロントエンド）に分けて実装します。

本リポジトリは、このゲームにおけるバックエンドサーバーを実装するものです。バックエンドサーバーでは、上記のようなゲームの開発にあたってサーバー側が担当すべきと考えられる基本的・中核的な機能を提供することを目指しています。現時点では、とりわけシンプルな機能とインタフェース（通信仕様）が実現されています。

そのため、現状の本サーバーの下では、様々なクライアントの実装が考えられます。クライアント側では、2Dゲームを実装することも、3Dゲームを実装することも可能です。また、プレイヤーがキャンパスの人々を銃で撃ち殺すことを競うようなクライアント実装も考えられますし、真っ先に握手しにいくことを競うようなクライアント実装も考えられます。

## 本サーバーの概要

### 大まかな仕様

* DTCL Platformから、本館入口付近に所在する人々（**ビジター**）の位置などを取得。
    * DTCL Platformの動体情報取得API（リアルタイム）を使用。
    * MQTTトピックは、`object/lidar/vista-p90-2/person`。
* クライアントとの通信は、WebSocketのみを用いて行われる。
* WebSocketの接続（connection）ごとに、**プレイヤー**を認識。
    * ユーザー登録のような機能はない。
    * Basic認証なども行われず、URLを知っていれば誰でもアクセスできる。
    * クライアントとのWebSocket接続が確立される（オープニング・ハンドシェイクが完了する）と、そのクライアントは、本サーバー上で新しいプレイヤーとして認識される。
    * クライアントとのWebSocket接続が終了する（クロージング・ハンドシェイクが完了するか、エラーにより接続が切断される）と、そのプレイヤーは本サーバー上から削除される。
* 本サーバーから、WebSocket接続中のクライアントに対して、以下の通りデータが送信される。
    * データの内容は、ビジターの位置、自他プレイヤーの位置、自他プレイヤーがビジターに接触（**タッチ**）した回数（**スコア**）など。
    * 送信は定期的に実施され、間隔は約0.1秒（DTCL Platformからの受信間隔と同じになる）。
* WebSocket接続中のクライアントは、本サーバーに対して、以下の通りデータを送信できる。
    * データの内容は、自分（自プレイヤー）の位置と、自分がタッチを試みているビジターのID。
    * 送信のタイミング・間隔は、クライアントの任意。
* クライアント側の不正（チート）を防ぐことは考慮外。
    * その反面、クライアント側では、様々な実装が可能。
* デバッグ・テスト・デモンストレーションなどの便宜のため、ダミーデータを使用する機能あり。

### デプロイとクライアント実装

本サーバーは、**すでにクラウドサービスへのデプロイが完了**しています。そのため、次章で説明する仕様に基づいて、実際に使用することができます。Cグループの皆さんにおいては、自由にクライアントの実装を試みて、本サーバーと通信していただいて構いません。

ただし、本サーバーは、総じて性善説に基づいています。前述の通り、ユーザー認証などの機能はありませんし、チートの防止は考慮されていません。また、大量・長大なデータを送り付けるような攻撃についても無対策です。

したがって、念のため、**URLを外部に流出させないでください**。クライアント実装にあたって、URLをハードコーディングしないようにするとか、GitHubリポジトリを非公開（プライベート）にするなど、ご対応をお願いします。

## クライアントとの通信についての仕様

本サーバーとクライアントの通信は、WebSocketのみを用いて行われます。**クライアントからの接続先URLについては、中野に聞いてください**。WebSocketプロトコルに関しては適当な文献をご参照いただきたいですが、ライブラリを使用すればプロトコルの詳細を理解しなくてもクライアントを実装できると思われます。

### ※福澤座標系

本サーバーにおいては、「福澤座標系」を採用しています。福澤座標系とは、SFCの福澤諭吉像を原点(0,0)とし、北に向かってX座標が増え、東に向かってY座標が増える座標系と定義します。後述①②③のいずれにおいても、X座標・Y座標は、この福澤座標系に基づきます。なお、単位はメートルとします。

必要であれば、クライアント側において、福澤座標系と任意の座標系を変換してください。福澤座標系と任意の座標系を変換する例については、[Pyxelクライアント（バックエンドサーバー検証用）で説明・図示](https://github.com/nakano89/digital-twin-pyxel-client?tab=readme-ov-file#%E5%8F%82%E8%80%83%E7%A6%8F%E6%BE%A4%E5%BA%A7%E6%A8%99%E7%B3%BB%E3%81%A8%E6%9C%ACpyxel%E7%94%BB%E9%9D%A2%E5%BA%A7%E6%A8%99%E7%B3%BB%E3%81%AE%E5%A4%89%E6%8F%9B)しているので、ご参照ください。

### ①オープニング・ハンドシェイク

オープニング・ハンドシェイクについては、基本的にWebSocketプロトコルの通りです。クライアント側においては、一般のWebSocketライブラリを使用すれば、自然とオープニング・ハンドシェイクが実装されるはずです。

ただし、本サーバー独自の仕様として、クライアントから送信されるハンドシェイクには、`digitaltwin-user-name`ヘッダ、`digitaltwin-user-x`ヘッダ、`digitaltwin-user-y`ヘッダを含ませる必要があります。このような独自のヘッダの追加はWebSocketプロトコルの許容するところであり、一般のWebSocketライブラリにおいて容易に対応できると思われます。これらのヘッダの値については、以下の通りとしてください。

* `digitaltwin-user-name`ヘッダ：自分を表現する任意の名前
    * ゲーム上に表示されることなどを目的とするプレイヤー名です。
    * 空文字列であることは許されません。
    * ASCII文字のみを含んでいる必要があります。
        * ASCII外の文字を表現するために任意のエンコードを施しても構いませんが、本サーバーは受信したままの文字列をプレイヤー名として扱って②本サーバーからの送信に含ませるため、デコードについてもクライアント側で対応してください。
    * すでに接続している他クライアントのプレイヤー名と重複する文字列は許されません。
        * オープニング・ハンドシェイクの前において、他クライアントのプレイヤー名を取得する方法はありません。
        * この点を気にするのであれば、オープニング・ハンドシェイクを試みた結果として本サーバーからHTTPステータスコード`400 Bad Request`が返された場合には、別のプレイヤー名で再試行するなどしてください。
* `digitaltwin-user-x`ヘッダ：自分の初期位置としての任意のX座標
    * 数値を表す文字列。
    * 整数でも小数でも構いません。負数でも構いません。
    * 後述「③クライアントからの送信」における`x`・`y`の説明についても参照してください。
* `digitaltwin-user-y`ヘッダ：自分の初期位置としての任意のY座標
    * 上記`digitaltwin-user-x`ヘッダと同様です。

オープニング・ハンドシェイクが完了すると、そのクライアントと本サーバーの間におけるWebSocket接続が確立されます。これにより、本サーバーは、そのクライアントに対して②本サーバーからの送信を定期的に実施するようになります。あわせて、クライアントは、いつでも本サーバーに対して③クライアントからの送信を実施できるようになります。

また、オープニング・ハンドシェイクが完了した時点で、そのクライアントは、本サーバー上で新しいプレイヤーとして認識され、②本サーバーからの送信にプレイヤーとして含まれるようになります。プレイヤーのスコアは0からスタートします。

### ②本サーバーからの送信

本サーバーからクライアントに対して送信されるデータの形式は、1種類のみです。これは、次のようなJSON文字列です。

```json
{
    "lidar_time": "2025-09-12T08:49:21.614651+09:00",
    "players": [
        {"name": "Nakano", "score": 6, "x": 125.10435567828893, "y": -45.737111409258056},
        {"name": "Tanaka", "score": 2, "x": 129.10329413826676, "y": -38.11699996565417}
    ],
    "touched_visitors": [
        {"id": 16092168, "x": 124.42013297518466, "y": -35.55533831728335},
        {"id": 16092145, "x": 123.76746981312866, "y": -42.67484166975898}
    ],
    "untouched_visitors": [
        {"id": 16091793, "x": 130.5839689027534, "y": -61.81984534207612},
        {"id": 16092147, "x": 115.99164844884203, "y": -39.866434462498425},
        {"id": 16092158, "x": 118.5482912889369, "y": -36.22818993177707}
    ]
}
```

* `lidar_time`：DTCL Platformにおいてビジターのデータが取得された時刻
    * 主として、後述「ダミーデータの使用」が有効にされた場合における活用を想定しています。
* `players`：プレイヤー（自プレイヤーも他プレイヤーも含む）の名前・スコア・X座標・Y座標
    * 自プレイヤーと他プレイヤーを区別したいときは、`name`で判別してください。
    * スコアは、接続開始（オープニング・ハンドシェイク）の時点で0に設定され、各クライアント（プレイヤー）がビジターへのタッチに成功するたびに1増えます。
* `touched_visitors`：プレイヤーから既にタッチされている現存するビジターのID・X座標・Y座標
* `untouched_visitors`：プレイヤーからまだタッチされていない現存するビジターのID・X座標・Y座標

なお、`players`、`touched_visitors`、`untouched_visitors`に関しては、後述「③クライアントからの送信」も参照してください。

以上のJSON文字列が、本サーバーから全クライアントに対して、定期的に送信されます。全クライアントに対して、同時に同内容のデータが一斉送信される形です。送信間隔は、DTCL Platformからの受信間隔に依存しますが、現状のところ約0.1秒のようです。

### ③クライアントからの送信

クライアントから本サーバーに対して送信できるデータの形式は、1種類のみです。これは、次のようなJSON文字列です。

```json
{
    "x": 133.023476922656369026,
    "y": 60.30682252659853526,
    "visitors_being_touched": [16092147, 16092158]
}
```

* `x`・`y`：自分の現在のX座標・Y座標
    * 本サーバーは、ここでクライアントから送信された位置を、そのまま②本サーバーからの送信におけるプレイヤーのデータに含めます。
    * クライアント側においては「1秒に最大10mしか移動できない」といった制約を設けてゲーム性を設計すると思いますが、本サーバーがそうした制約を課すことはなくチート的な動きも可能です。
* `visitors_being_touched`：タッチを試みているビジターのID
    * クライアントは、まだ他プレイヤーからタッチされていないビジター（②本サーバーからの送信に含まれる`untouched_visitors`）に対して、自らのプレイヤーがタッチできたと判定したときは、そのビジターのIDをここに含めて本サーバーに報告してください。
    * しかし、②本サーバーからの送信の時点では他プレイヤーからタッチされていない現存するビジターであっても、わずかな時間差で、すでに消滅していたり、他プレイヤーにタッチされていたりする可能性があります。
    * そこで、本サーバーは、報告を受けた時点において現存していないビジターについて、タッチを受け付けず、スコアにカウントしません。
    * また、本サーバーは、あるビジターについて、最初にタッチを報告してきたクライアント（プレイヤー）のスコアのみを1増やします。
    * クライアント側においては「0.5m以内に近づいたらタッチ判定する」とか「銃で撃った弾が当たることをもってタッチと判定する」といったルールを設けてゲーム性を設計すると思いますが、本サーバーがそうした制約を課すことはなく、この点においてチートは可能です。

以上のJSON文字列を、クライアントは本サーバーに対して、任意のタイミングで送信することができます。なお、`x`・`y`・`visitors_being_touched`のいずれも省略することは許されず、タッチできたと判定されたビジターが存在しないときは`visitors_being_touched`は空の配列`[]`にしてください。また、上記形式に沿わないJSON文字列、JSONとして解釈できない文字列、バイナリデータが送信された場合、本サーバーはWebSocket接続クローズコード`1008 Policy Violation`を返してWebSocket接続を終了します。

以上のデータを送信したとしても、これに対応する返信（サーバからのデータ送信）はありません。タッチが成功したか否かは、②本サーバーからの送信に含まれる自分のスコアが増えたか否かにより確認してください。もっとも、クライアントは、一度に複数のビジターへのタッチを試みるような場合において、どのビジター（ID）へのタッチが成功したか判断する方法はなく、スコアの変化しか認識できないことにつきご了承ください。

### ④接続の終了（クロージング・ハンドシェイク）

クライアントは、本サーバーとの接続を終了したければ、クロージング・ハンドシェイクを開始するか、何ら手続きを実施せずに通信を終了（切断）してください。クロージング・ハンドシェイクによる接続の終了は、本サーバーに素早く接続の終了を伝えることができるので、望ましい方法です。他方、クライアントが何ら手続きを実施せずに通信を終了したとしても、本サーバーは数十秒後には接続の終了を認識します。

クロージング・ハンドシェイクについては、WebSocketプロトコルの通りです。クライアント側においては、一般のWebSocketライブラリを使用すれば、容易にクロージング・ハンドシェイクの開始を実装できるはずです。

どのような形によってクライアントと本サーバーとの接続が終了されたとしても、そのクライアントは本サーバー上のプレイヤーから削除されます。クライアントがクロージング・ハンドシェイクによって接続を終了した場合には、クライアントが何ら手続きを実施せずに通信を終了した場合よりも、素早く本サーバー上のプレイヤーが削除されます。とはいえ、最終的な結果に変わりはありません。

なお、本サーバー側が、自発的に接続を終了させる（クロージング・ハンドシェイクを開始する）ことはありません。ただし、③クライアントからの送信が不正であるために`1008 Policy Violation`を返してWebSocket接続を終了する場合と、Ping送信に対する迅速なPong応答（これはWebSocketプロトコルにおいて義務付けられているものにすぎず、一般的なライブラリを使用するのであれば意識的に実装する必要はないことが多いと思われます）をクライアントが実施しない場合においては、この限りではありません。

### ※意図しない接続の終了

WebSocket接続の終了（切断）は、クライアント・本サーバーともに意図しない場合であっても、起こってしまうことが少なくありません。これは、WebSocketの性質上、仕方がないと考えられます。クライアント側の不安定なWi-Fi環境などにより通信が一定時間途絶えるとWebSocket接続は終了されてしまいますし、不明な原因によりWebSocket接続が終了することも珍しくないようです。

確率的には、接続時間が長くなるほど、どこかの時点で切断が起こってしまう確率が増加します。あえて中野の環境における大まかな感覚を述べると、数分以内にWebSocket接続が意図せず切断されることは少ないですが、逆に数時間にわたってWebSocket接続が維持されることも少ないです。

通常は、このようなWebSocketの性質（というかインターネットの性質）をふまえて、再接続の処理を実装します。ただし、現状の本サーバーは、ユーザー認証を行わないという便宜のために、WebSocket接続ごとにプレイヤーを認識しています。そのため、WebSocket接続が終了すると、スコアが0にリセットされることは避けられません。クライアント側において自動で再接続する機能を実装して良好なユーザー体験を目指していただいても構いませんが、スコアはリセットされることにつきご了承ください。

### ※受信は高頻度で、送信は低頻度で

クライアントが本サーバーと通信するにあたっては、「受信は高頻度で、送信は低頻度で」を心がけてください。そうすることで、②本サーバーからの送信される情報が素早くゲームに反映されるとともに、意図せずWebSocket接続が終了してしまう確率が減ると思われます。

クライアント側の受信処理（②本サーバーからの送信）については、十分に短い間隔で実施してください。②本サーバーからの送信は約0.1秒おきに実施されるため、基本的に0.1秒よりも短い間隔で受信処理を継続しないと、本サーバー側の情報とクライアント側のゲーム画面などにラグが生じてしまいます。一時的に処理が滞って数秒分の受信データがたまってしまうことも考えられますが、0.1秒よりも十分に短い間隔で受信処理を実施していれば、そのうちラグは解消されます。なお、受信処理の間隔を短くする代わりに、1度の受信処理においてたまっている受信データをまとめて解消する実装も考えられます。また、ライブラリによっては、そうした処理を提供する関数などがあるかもしれません。

クライアント側の送信処理（③クライアントからの送信）については、過度に高頻度にならないようにしてください。本サーバーが許容できるよりも高頻度でデータを送信すると、本サーバー側が強制的にWebSocket接続を切断してしまったり、本サーバーが落ちてしまったりする可能性があります。もっとも、本サーバーはそれほど重い処理を行っているわけではないので、あまり気にしすぎる必要はありません。少なくとも、本サーバーからの送信間隔に合わせて、クライアントから0.1秒ごとにデータを送信する程度では、高頻度すぎることはないと思われます。

実装例として、[Pyxelクライアント（バックエンドサーバー検証用）](https://github.com/nakano89/digital-twin-pyxel-client)の`main.py`を参考にしてください。この実装例では、毎フレームにおいて（FPS=30に設定しているので約0.03秒ごとに）、たまっている受信データをすべて処理して、最新の受信データのみを使用するようにしています。他方、データ送信については、毎フレーム実施するのではなく、データ受信があったフレームにおいてのみ（要するに約0.1秒おきに）実施しています。

## ダミーデータの使用

本サーバーは、実際にDTCL Platformからリアルタイムに取得されるデータに代えて、本サーバー上に保存されているダミーデータを使用する機能を有しています。この機能を有効にすると、本サーバーは、あたかもダミーデータがリアルタイムに取得されているかのように振る舞います。②本サーバーからの送信に含まれる`touched_visitors`・`untouched_visitors`の情報についても、③クライアントからの送信で報告される`visitors_being_touched`による本サーバー上でのタッチ成否判定・スコア加算についても、ダミーデータに基づくようになります。

ダミーデータの使用が有効になっているとき、ダミーデータが末尾まで使用されると、先頭に戻って再度使用されることが繰り返されます。ダミーデータが先頭に戻るとき、本サーバー上において、プレイヤーのスコアは維持されますが、ビジターについてのタッチ済みの記録はリセットされます。これにより、ダミーデータが一周するたびに、プレイヤー（クライアント）は、いずれかのプレイヤーが過去にタッチしたビジターに対しても、再度タッチできるようになります。そうしなければ、ダミーデータの使用下において、クライアントがプレーを続けると、まだタッチされていないビジターがいなくなってしまうからです。

現在、ダミーデータを使用する機能は有効になっています。具体的には、2025年9月12日(金)午前8:46-8:50頃の約4分間のデータが繰り返し使用されています。実地テストを除いて、デバッグ・テスト・デモンストレーションを実施するときは、ダミーデータのほうが都合がいいと思われます。

なお、クライアントの実装にあたっては、ダミーデータに関して意識する必要はありません。ただし、ダミーデータが使用されているか否かをユーザーに伝えたければ、②本サーバーからの送信に含まれる`lidar_time`を表示することが考えられます。
